# ความเสี่ยงที่ต้องระวัง (Risk Register)

เรียงตามผลกระทบ — ข้อ 1 กระทบสถาปัตยกรรมโดยตรง ต้องออกแบบให้ถูกตั้งแต่ตัว Follow-up Engine ตัวแรก

## 1. Meta 24-hour messaging window ⚠️ สำคัญที่สุด

Facebook ห้ามส่งข้อความโปรโมชั่นเกิน 24 ชม.หลังลูกค้าทักล่าสุด ยกเว้นผ่านกลไกที่กำหนด — กระทบฟีเจอร์ Follow-up/Cross-sell โดยตรง (ถ้าไม่ระวังเสี่ยงโดนแบน Page)

**ข้อเท็จจริงสำคัญ:** window เปิดใหม่ทุกครั้งที่ลูกค้าทักมา ไม่ใช่มีครั้งเดียวจบ — ข้อจำกัดเกิดเฉพาะตอนเราทักออกไปเองหลังลูกค้าเงียบเกิน 24 ชม.

**วิธีป้องกัน (ต้องฝังเป็น business rule ในโค้ด ไม่ใช่ปล่อยให้ AI ตัดสินใจเอง):**
```
Follow-up จะส่งอะไร ต้องเช็ค 2 อย่างก่อนเสมอ
1) ลูกค้าทักมาใน 24 ชม.ล่าสุดไหม → ใช่ = ส่งอะไรก็ได้
2) ถ้าไม่ใช่ → เนื้อหาคืออะไร
   - สถานะออเดอร์/จัดส่ง → ส่งได้ (Post-Purchase Update tag)
   - เสนอขาย/cross-sell → ต้องผ่าน LINE (ง่ายกว่า, default) หรือ FB Marketing Messages (ต้องขอ opt-in ในแชทก่อน + ผูก ad account + รอ Meta review)
```

## 2. อย./สคบ. — AI อ้างสรรพคุณเกินจริง (กลุ่มความงาม/สุขภาพ)

พ.ร.บ.เครื่องสำอาง 2558 + พ.ร.บ.คุ้มครองผู้บริโภค ม.22 ห้ามอ้างสรรพคุณเกินขอบเขต ("รักษา", "หน้าใส 100%") — ร้านค้าเป็นผู้รับผิดชอบทางกฎหมาย แต่กระทบความน่าเชื่อถือแพลตฟอร์มถ้าเกิดบ่อย

**วิธีป้องกัน:** ตั้งคำต้องห้ามใน system prompt + ตรวจ output ก่อนส่งจริง โดยเฉพาะ tenant กลุ่มความงาม/สุขภาพ

## 3. PDPA — ต้องมีสัญญากับร้านค้าทุกราย

เรามีสถานะเป็น **Data Processor** (ประมวลผลข้อมูลลูกค้าปลายทางของร้านค้า) ตาม PDPA ต้องมีสัญญาเป็นลายลักษณ์อักษรกับร้านค้าทุกราย + มาตรการความปลอดภัยตามมาตรฐาน + เก็บ log การประมวลผล

การเก็บพฤติกรรมลูกค้าเพื่อแนะนำสินค้าแบบ personalize ต้องมี **opt-in consent แยกต่างหาก** (ไม่ใช่แค่ยอมรับ T&C ทั่วไป) พร้อมทางเลือก "ปฏิเสธ" ที่ใช้งานได้จริง

**วิธีป้องกัน:** click-to-accept DPA ตอน onboarding (log tenant_id, เวอร์ชัน, timestamp, IP) + opt-in message ในแชทครั้งแรกที่ครอบคลุมทั้ง Meta Marketing Messages และ PDPA profiling พร้อมกัน

## 4. LINE OA cost ที่ตกเป็นภาระร้านค้า

Broadcast/Push message นับโควตา (ฟรี 200 ครั้ง/เดือน) แต่ **Reply message ฟรีไม่จำกัด** — วันที่ลูกค้าทักเข้ามาเยอะ (ไวรัล) ไม่กระทบโควตานี้เลย มีผลเฉพาะตอนร้านทัก broadcast/follow-up ออกไปเอง

**วิธีป้องกัน:** แจ้งค่าใช้จ่ายแยกให้ชัดตอน connect LINE (ไม่ใช่ซ่อนใน T&C) + มิเตอร์เตือนโควตาใกล้หมดในแดชบอร์ด

## 5. Prompt Injection — ลูกค้าหลอก AI ให้พูด/ทำสิ่งที่ไม่ควร

เคสจริง: ตัวแทน Chevrolet โดนหลอกจนบอทตกลงขายรถ $1 กลายเป็นไวรัล — ระบบนี้เสี่ยงกว่าเพราะ AI มีสิทธิ์ `createOrder()`/เสนอส่วนลดจริง

**วิธีป้องกัน:** แยกสิ่งที่ AI "พิมพ์ในแชท" กับสิ่งที่ระบบ "ยอมให้ทำจริง" เด็ดขาด — ก่อน execute action (สร้างออเดอร์/ใส่ส่วนลด) ต้องผ่านการตรวจสอบแยกอีกชั้นในโค้ด ไม่เชื่อสิ่งที่ AI สรุปมาตรงๆ

## 6. Gemini API ไม่เสถียร (165+ outage รายงานในรอบ 1 ปี) + Rate limit

ถ้า Gemini ล่ม ทุกร้านบนแพลตฟอร์มหยุดตอบพร้อมกันหมด (ต่างจากระบบที่พังทีละร้าน) — free tier จำกัดแค่ 15 RPM ด้วย

**วิธีป้องกัน:**
- ห้ามอยู่ free tier — เปิด billing ให้ได้ Tier 1 (150-300 RPM) ตั้งแต่มีลูกค้าจริง
- Message Router (Level 1-2 ตอบจาก DB/Rule) ทำงานได้แม้ Gemini ล่ม — เป็นเกราะกันดับพร้อมกันในตัวอยู่แล้ว
- ตั้ง fallback message + auto handoff เข้า Human Inbox เมื่อเรียก Gemini error แทนที่จะปล่อยลูกค้าเงียบหาย
- มีคิว/retry เมื่อชน rate limit ช่วงลูกค้าทักเยอะพร้อมกัน (viral day) แทนที่จะ error ทิ้งเฉยๆ

## 7. Token/Credential security

ห้ามเก็บ Facebook/LINE token เป็น env var ตัวเดียว (รองรับได้แค่ page เดียว) — ต้องเป็นตารางเข้ารหัสต่อ page/OA พร้อม status (`CONNECTED`/`TOKEN_ERROR`/`PERMISSION_REVOKED`/`DISCONNECTED`/`RECONNECT_REQUIRED`) และมี UI ให้ร้านเห็น/reconnect เองได้

## 8. Tenant isolation

ทุก query ต้องกรอง `tenant_id` — บั๊กจุดนี้เท่ากับข้อมูลร้านหนึ่งรั่วไปอีกร้านหนึ่ง เป็นความเสี่ยงร้ายแรงสุดถ้าเกิดขึ้น ต้องมี automated test คอยเช็ค ไม่ใช่ตรวจด้วยตาเปล่า

## 9. Payment collection gap

"ปิดการขาย" ต้องมีระบบยืนยันว่าลูกค้าจ่ายเงินจริง (เช็คสลิป/PromptPay callback) ก่อนเปลี่ยนสถานะออเดอร์ — ยังไม่ได้ออกแบบละเอียด ต้องทำก่อน Phase 2 (ดู requirements)

## 10. Meta Business Verification timeline

ก่อนเปิดขายลูกค้าภายนอกจริง ต้องผ่าน Business Verification + App Review (`pages_messaging` Advanced Access) — ใช้เวลาหลายสัปดาห์และอาจถูก reject ถ้าเอกสารไม่ครบ ต้องเผื่อ buffer เวลาไว้ใน timeline การเปิดขาย ไม่ใช่คิดว่าเขียนโค้ดเสร็จแล้วขายได้ทันที
